# 任务包 m4-4.1 · 处置能力声明（后端）

## 目标

实现 `disp_get_capabilities` Tauri 命令：给定 `refId`，返回该引用当前可用的处置操作集合（archive / softDelete / destroy / restoreFromBin），并携带每项的 `reason`。同时补全 `storage_source.caps_json` 的探测逻辑（启动时探测系统回收站可用性写入 `softDelete`）。

这是 M4 所有处置操作的前置依赖 —— UI 根据能力决定渲染哪些按钮，后续 4.2~4.7 都以此为基础。

## 需求与设计出处

- 详细设计说明书 §2.6 `disp_get_capabilities`（**契约冻结**）
- 详细设计说明书 §5.1 系统回收站（`caps_json.softDelete` 由启动探测写入）
- 详细设计说明书 §6.7（能力为 false 必须给 reason）
- 开发计划 M4-4.1 验收点：能力正确返回

## 接口契约（摘自详细设计 §2.6，逐字段对齐）

**入参**：`{ refId: string }`

**出参**：
```json
{
  "archive": true,
  "softDelete": true,
  "destroy": true,
  "restoreFromBin": true,
  "reason": { "softDelete": "ok" }
}
```

**关键语义**：
- `archive`：`disposition != 'archived'` 时 true；已归档则 false，reason 说明
- `softDelete`：取决于 `storage_source.caps_json.softDelete`；引用所在存储源不支持回收站时 false，reason 说明（Linux 无回收站场景）
- `destroy`：始终 true（销毁是兜底）
- `restoreFromBin`：`disposition == 'deleted'` 时 true；否则 false
- `reason`：只给 false 项填说明（字符串），true 项可省略或填 `"ok"`

**错误**：`COMMON_NOT_FOUND`（refId 不存在）

## 要求

1. **能力计算为纯函数**：输入 `(reference_row, caps_json)`，输出 `DispCapabilities`；单测覆盖所有组合。
2. **启动探测**：用 `trash` crate 或平台 API 探测回收站可用性；Linux 无回收站时把 `caps_json.softDelete` 置 false。**不引入 trash crate 作为本任务依赖**（4.4 才接入执行删除）—— 探测可用简单方法：检查平台 + `XDG_DATA_HOME/Trash` 存在性；macOS/Windows 默认 true。
3. **单元测试**：
   - 不存在 refId → `COMMON_NOT_FOUND`
   - disposition 为 none / archived / deleted 三种状态下各字段正确
   - caps_json.softDelete=false 时 softDelete=false 且 reason 说明
   - 已归档时 archive=false 且 reason 说明
   - 已删除时 restoreFromBin=true
4. 不引入新第三方依赖。
