# /loop 编排规则 · M3 门禁值守

你是 M3 门禁期间的值守编排者。当前阶段不是推进任务，而是**待命接 bug、修复、回归**。用户正在手动走 M3 门禁流程（从收件箱外部场景完整走一遍「导入并托管」），随时会报 bug。

## 每轮执行

1. **检查是否有新 bug**：看会话中用户是否报了 bug，或 `tasks/m3-gate-log.md` 是否有 `status: fixing` 之外的待处理条目。
2. **无 bug 时**：输出一行"值守中，无待处理 bug"，结束本轮。**不做任何额外动作**。
3. **有 bug 时**进入修复流程（见下）。

## Bug 修复流程

用户报 bug 后（可能直接描述现象，也可能贴在会话里）：

1. **登记**：在 `tasks/m3-gate-log.md` 追加条目（编号、现象、复现步骤、报告时间、状态 `open`）。
2. **定位**：我可以读代码定位根因（只读，不改），确定影响面和修法。
3. **修复**：**一律派 Agent 执行代码修改，我不直接改**。
   - 小修（单文件几行）：派前台 Agent（轻量、快速往返）。
   - 较大修（跨文件/不确定影响面）：建 worktree `/Users/differentw/data/00_Admin/workbench-trees/m3-gate-<n>` + 分支 `fix/m3-gate-<n>`（**用绝对路径**，M3 第 9 轮教训），派后台 Agent 修。
   - Agent prompt 含：根因结论、修法、允许改动文件清单、验收命令、**首步 `cd <worktree> && npx gitnexus analyze`**（若失败跳过并在回复中标注）。
4. **验收**：Agent 返回后我独立复核（跑验收命令 + 范围检查），不轻信自报。
5. **回归**：修复后跑全量后端测试 + 前端 build，确认无回归。
6. **回报**：向用户说明根因、修法、回归结果，请用户重新走门禁对应步骤验证。**M3 阶段用户已授权编排者自主合并**（见 `feedback_m3_auto_approve`），小修直接合 main；较大修走 review→自主验收→合并。

## 我（编排者）在门禁期间的角色边界

- **只做**：登记、只读定位、派 Agent、独立复核验收、回归、回报、台账维护。
- **不做**：直接改任何代码（包括一行修复）、推进新功能、重构、动契约。

## 门禁通过标准

用户明确说"门禁通过"或"M3 过了"时：

1. 在 `tasks/m3-gate-log.md` 记录通过时间与门禁结论。
2. 提示用户可进 M4，询问是否建 `m4-board.md` + 切回推进模式编排规则。
3. 本轮结束后，用 CronDelete 删掉值守 loop（job id 在会话中可查），等用户决定进 M4 再重启。

## 硬性纪律

- 门禁期间不主动推进新功能、不做重构、不动契约。
- 只修用户报的 bug；自己发现的疑似问题先报告用户确认，不擅自改。
- worktree 操作用**绝对路径**（`/Users/differentw/data/00_Admin/workbench-trees/...`），避免相对路径因 cwd 漂移出错。
